# 0014. 仅沟通 Paging Bounded by an Execution Cursor Read Back from Task Records

> **SUPERSEDED by [ADR 0015](0015-opening-screen-only-check-chat-scan.md) (2026-09-23).** The scan still kept paging on a live device, so `CHECK_CHAT` no longer pages at all: it reads the opening screen and stops. The cursor, the card-stamp parser and `list_recent_successful_completions` were removed with it; this record is kept as the history of the approach and its accepted limitations. The implementation is in git history at `c490138`.

We decided that the rejection cleanup (`CHECK_CHAT`) stops paging the 仅沟通 list once it reaches cards older than the previous run that actually acted, that the opening page is read in full regardless, that the cursor is derived from the broker's own SUCCESS task records rather than kept in a collection of its own, and that a card's age is compared at the resolution the platform rendered it at.

## Context

Running the cleanup against a long 仅沟通 list exposed three properties of the list and the scan:

- **Depth bounds do not bound this list.** `max_scan_depth` bounds *LLM evaluations*, and a card carrying the Outbound Message Indicator is skipped before any evaluation. A backlog of threads waiting on a recruiter reply therefore costs nothing per card and scrolls on until the separate `MAX_INSPECTED_CARDS` (300) ceiling — which is the list this work exists for (issue #239).
- **Every run re-judged the newest cards.** The scan always began at the top, and a preserved card (a genuine invitation, a message that is not a rejection) is never removed from the list, so each dispatch handed the same few cards to the classifier again, one call each.
- **The list is ordered newest-first**, so "everything below this point was already judged by a run that got this far" is a property the list itself provides — as long as a run can find out how far the last one got.

Card stamps are also rendered as localised text at two different resolutions: an instant (`14:30`, `昨天 10:20`) or a whole day (`09-21`, `2023-11-04`).

## Decision

1. **The page stop line is the previous run's completion time.** Once the run has scrolled away from the opening page, a card that is *provably* older than that line ends the scan with `stop_reason="reached_last_execution_time"`, which is logged with the stamp and the sender of the card that marked it. Cards past the line are not re-judged, and a card sharing the boundary viewport that is not provably older is still judged before the stop.
2. **The cursor is derived, not stored.** `BaseTaskBroker.list_recent_successful_completions(task_type, limit)` returns a task type's most recently finished SUCCESS runs, newest first, and the handler reads the completion instant off the newest one that acted. A SUCCESS task record already *is* the durable record of a run's completion, so deriving from it cannot drift from the runs it describes and needs no collection to provision. (A dedicated `task_cursors` collection was considered and rejected by the repo owner on that basis.)
3. **A dry run never supplies a cursor.** A dry run succeeds without acting, so trusting one would hand the next real run a window starting *after* the messages the dry run declined to touch, and no later run would revisit them.
4. **The opening page is unconditional, and the exemption ends at the first scroll** — not at the first pass of the scan loop. Acknowledging a rejection round-trips through the chat and back to the same screen, which the run then re-reads; keying the exemption on the loop's first pass would put the stop line in force over cards the run never scrolled past. The opening page is the only place a state the previous run never saw can be sitting, so it is read whatever its stamps say.
5. **A stamp is compared at its own resolution.** Card times carry no seconds and no timezone, so `CardTimestamp.is_before` floors a minute-precision comparison to the minute and a day-precision one to the day: a `09-21` card is not older than a cursor still inside 09-21, and a `14:30` card is not older than a cursor at `14:30:59`. Reading a coarse stamp as an exact instant would truncate the boundary period and drop the messages inside it, which no later run would revisit. An unreadable stamp is *unknown*, never "old", so it is judged rather than truncated on.
6. **A cursor from the future is refused.** Task records are stamped by PocketBase's clock and card stamps by the device's, and a cursor a few minutes ahead of the device would put the stop line above every card on the list, ending paging before a single message was read. A completion time more than `MAX_CURSOR_SKEW_SEC` (300s) ahead is reported in the task log and the run scans in full instead.
7. **The stamp is read through a parse gate.** `communication_list.card_time` carries four candidates, and both the located field and the child-`TextView` fallback must *parse* as a stamp before either is used, so a wrong resource-id or a borrowed text node cannot hand the scan a plausible-looking string to truncate on. The four candidates are paid once per card per viewport, alongside the four the row already spends (name, message, status, descriptor) — a different cost profile from the per-recovery-step probe ADR 0011 limited, which is why the amendment there does not cap this list.

## Trade-offs

- **A run that stops short of its own stop line still advances the cursor.** `max_scan_depth`, `MAX_INSPECTED_CARDS`, `stalled` and `lost_list` all end a scan early while still reporting success, so the stretch of window such a run never reached is older than the next run's stop line and no later run revisits it — `lost_list` (the platform failing to return to the list after an acknowledgment) is the most likely of the four. **Accepted deliberately on 2026-09-23**, when the implementer raised it and the repo owner chose to record the limitation rather than extend the broker's write path with a coverage marker. Two things bound the loss: the stretch that a *ceiling* cut off was already unreachable before this ADR (a `max_scan_depth`-limited run never reached it either), so the regression is confined to the region between the previous stop line and the previous run's end; and a run stopped by a *lost list* still blacklists and acknowledges every rejection it saw. Whoever revisits this should make a run that did not reach its stop line ineligible as a cursor, which needs the coverage fact persisted on the run's own task record.
- **A dry run can no longer preview the whole list.** Once a cursor exists, `dry_run` truncates exactly as a live run does, so a drill-mode preview covers the new part of the list only. There is no payload override to ignore the cursor; add one if previewing the full list is wanted.
- **The first-ever run still stops at the depth and card bounds**, since it has nothing to measure against, and so does any run whose cursor was refused as skewed.
- **`CommunicationCard` gained a fifth per-card probe** (`communication_list.card_time`), and the child-node scan behind it is a full tree walk when every id misses — paid once per card, and only on a device whose ids differ from the configured ones.
